# `/管理 成员id` 使用与维护

本功能仅通过 Bot 的官方 Discord REST 客户端读取成员列表，不使用用户 Token、Self-bot、成员缓存或 Gateway 全量成员抓取。默认 TXT，每行一个用户 ID，包含 Bot 账号；不写入用户名、头像、邮箱等信息。

## 部署前检查

1. 沿用项目现有 Node.js、`npm ci` 和启动方式，无新增依赖或权限配置。
2. 在 Discord Developer Portal 确认 **Server Members Intent** 已启用，并在需要时获得 Discord 对 privileged intent 的批准。40 万成员服务器适用的审批、验证要求须由应用所有者确认。源码已有 `GatewayIntentBits.GuildMembers`，这不能证明后台授权已批准。
3. 确保 `data/` 为可持久化磁盘，Bot 进程可写，磁盘空间充足。新增的 `data/member-id-export/` 已被现有 `.gitignore` 的 `data/` 规则排除；不要提交或对外托管该目录。
4. 按现有 `GUILD_IDS` 配置启动后，现有 `clientReadyHandler` 会同步 `/管理` 的新结构。没有新增顶层指令。原有 `/管理 关门` 的可选「恢复时间」参数和 `/管理 开门` 保持原行为。
5. 先在测试服务器执行「检查」，再由管理员决定是否在目标服务器执行「开始」。本次开发测试不访问真实 Discord 成员 API，不部署生产环境，不自动创建全服导出任务。

## 指令

| 指令 | 行为 |
| --- | --- |
| `/管理 成员id 检查` | 成员列表 `limit=1` 实测；额外请求 Guild `with_counts=true` 获取近似人数。区分本地 Intent 配置与实际 REST 可访问性，不创建任务。 |
| `/管理 成员id 开始` | 先持久化任务，立即私密回复任务 ID、初始状态及已提交数量，随后后台执行。同服已有活动任务时返回原任务；最近任务失败时从原断点续传；完成后再次开始会创建新任务。 |
| `/管理 成员id 状态` | 当前服务器最近任务的 ID、状态、唯一 ID 数量、非空分页数、进度更新时间、累计应用层重试、最近错误、下次重试时间。完成时展示实际数量与 SHA-256。没有伪造百分比。 |
| `/管理 成员id 下载` | 只接受当前服务器最近的已完成任务；重新验证文件摘要、行数、字节数。下载前及每个附件发送前重新刷新调用者权限。附件仅随私密 Interaction 返回。 |

四个操作都调用现有 `checkAdminPermission()` 和 `getPermissionDeniedMessage()`，支持现有服务器所有者、原生管理员和公共函数定义的管理身份组。没有新增白名单或复制身份组 ID。每次操作刷新服务器所有者、角色权限及**单个调用者**的成员数据，网络失败时拒绝授权。旧关门/开门权限路径未改变。

## 可靠性与性能

- 复用 `client.rest.get(Routes.guildMembers(guildId))`，每页 `limit=1000`，游标从字符串 `0` 开始，取当前页最大 Snowflake。即使不足 1000 条也继续到成功的空页；错误响应绝不视作分页结束。
- Snowflake 按字符串存储和交付，比较仅用 `BigInt`。SQLite 唯一键 `(job_id,id)` 去重，不长期保留成员对象或全量 ID Set。
- 复用项目已有 `better-sqlite3`，使用独立的 `exports.sqlite`，与其他模块数据库隔离。WAL + `synchronous=FULL`；每页事务同时插入 ID、更新唯一计数和 `after`。事务异常全部回滚；崩溃后从最后已提交页继续，不会只保存游标而漏存数据。
- 同服活动任务由 SQLite 部分唯一索引限制；worker 使用 90 秒持久化租约，每 15 秒续期，所有提交校验租约归属。每个 Bot 进程串行执行任务。轮询每 30 秒；重启后仅恢复原有未完成任务，崩溃遗留租约最多约 120 秒后被接管。正常退出会中止请求并释放租约。
- discord.js 自带 bucket/global 429 管理和网络超时；外层请求总时限 120 秒（包含排队及内部重试）。429、5xx、常见网络错误最多额外重试 5 次，采用指数退避（1/2/4/8/16 秒加随机抖动；上限 30 秒），并尊重更长的 `retry_after`。重试耗尽转为失败，保留诊断与断点，管理员可再次「开始」续传。401/403 不反复重试。
- 最终文件以每批 1000 行从 SQLite 读取并增量写入临时文件，`fsync` 后重命名并同步目录项，再独立流式校验 SHA-256 和行数，与数据库唯一计数比对，全部通过才标记完成。新任务目录也同步到父目录；文件系统不支持目录同步时明确失败。无效 ID、未知倒退 ID 或停滞游标会失败。
- 使用 Interaction 提供的 `attachmentSizeLimit`，旧 discord.js 无该属性时保守使用 8 MiB。超限时按完整行生成多个 TXT；每个私密回复发送一个附件，不截断或丢弃数据，无需额外 ZIP 库。下载准备失败时不发送文件。传输中断可能已交付部分分片，需重新执行「下载」获取整组文件；分片带序号。

## 保存、清理与安全边界

目录权限为 `0700`，数据库和导出文件为 `0600`。文件名、任务 ID 均由服务生成；Slash Command 不接受路径、文件名、任意任务 ID 或其他服务器 ID。SQL 查询始终按当前服务器查任务。日志仅记录任务 ID 和简短错误，不记录成员列表或原始 API 响应。导出结果不发送公共频道或第三方存储。

已完成和失败任务保留 **24 小时**，启动时及每小时清理过期文件、任务与 ID 行；周期清理意味着通常在完成/失败后 24–25 小时移除。活动任务保留以便恢复。下载使用持久化、定期续期的保留锁；清理先原子标记过期，阻止新下载，再删文件和数据库记录，避免与下载交错。保留锁续期失败会停止后续交付，不影响 Bot 进程。分片临时目录在下载结束或失败时移除；生成或发布失败会立即删除本次未发布文件。清理也会独立按文件年龄回收超过 24 小时的未引用 TXT/临时文件/废弃下载目录，包括活动任务目录内的崩溃残留，保留已发布文件及仍有效的下载锁。SQLite 释放的空间供后续导出复用，因此数据库文件本身可能保留历史最大容量；文件系统快照或外部备份的删除由主机维护者负责。

本机管理员仍能读取受控目录，需按项目现有主机和备份权限管理。Discord Ephemeral 附件仍由 Discord 托管；Bot 只能对每次新下载重新鉴权，无法撤回用户已经下载到本地的内容。

## 一致性限制

Discord 的成员列表 API **不提供原子成员快照**。导出期间加入/离开、长时间断线后续传，都可能导致结果与某一时刻的服务器人数不同。例如在游标之前加入的较早 Snowflake 账号可能无法在本轮遍历中出现，已读后离开的成员也可能仍在结果中。完成意味着官方 `after` 分页到达空页、取得的 ID 已去重且文件通过校验，不代表一个不可能保证的瞬时快照。需要更新结果时，在完成后重新执行「开始」。

## 验证

按本次交付要求，新增测试文件仅保留在开发工作区，**不提交、不进入 PR**；原有测试和 `npm test` 占位脚本保持不变。工作区验证命令为 `node --test tests/memberIdExport/*.test.js tests/selfModeration/*.test.js`，Node 22 逐项输出命令为 `node --test --experimental-test-isolation=none tests/memberIdExport/*.test.js tests/selfModeration/*.test.js`。PR 检出后仅有原有测试，可直接运行 `node --test tests/selfModeration/*.test.js`。

本地新增测试使用临时目录、真实 SQLite、模拟 REST；另有一个真实 discord.js REST 客户端测试，仅以本地 `makeRequest` 替身返回 429/200，完全不访问 Discord。

覆盖原有命令注册/路由/开关门执行、公共鉴权、撤销权限、跨服隔离、分页/去重/大整数、事务回滚、失败和重启续传、并发租约、403/429/5xx/断网/超时、摘要损坏、分片、保留锁、清理，以及 400,000 成员压力场景。模拟结果不等于真实服务器验证；后台 Intent 审批、目标服务器 API 可访问性及真实 Discord 附件交付仍需应用所有者在测试环境人工确认。

本次验证环境为 **Node 22.23.4**，92 项测试全部通过（包含子测试）。40 万模拟成员使用 401 次 REST 请求、400 个非空分页，最终 TXT 为 400,000 行、7,600,000 字节；本次观测堆增长约 9.1 MB，不代表所有主机的内存上限。另包含子进程在 SQLite 事务中直接退出的崩溃恢复测试，以及只读审查所发现的目录同步、未发布文件回收、下载锁异常的回归测试。

测试环境默认 Node 24.19.0 曾在 `better-sqlite3@11.10.0` 原生对象回收时触发进程断言；本次未调整现有依赖、运行版本配置或启动命令。若主机使用 Node 24，需先人工验证现有原生依赖兼容性。本地 `npm test` 仍保留原来的固定报错占位行为，以上直接执行测试文件的命令是本次验证依据。
